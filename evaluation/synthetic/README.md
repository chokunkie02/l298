# ชุดข้อมูล OCR สังเคราะห์ (Synthetic Dataset Generator)

โฟลเดอร์นี้เป็นโครงสร้างสำหรับสร้างภาพ OCR **สังเคราะห์** (render ข้อความที่รู้
ground truth แน่นอนด้วยฟอนต์ แล้วจำลองสภาพกล้อง เช่น แสง มุม เบลอ noise)
ผ่าน `generate_synthetic_ocr.py` เพื่อทดสอบ pipeline preprocessing/evaluation
และหาข้อบกพร่องเชิงระบบ (systematic weaknesses) ได้เร็วและทำซ้ำได้แน่นอน

## ข้อจำกัดสำคัญที่ต้องเข้าใจก่อนใช้งาน

**ชุดข้อมูลสังเคราะห์นี้ไม่ใช่ตัวแทนของภาพถ่ายจริงจากกล้อง/มือถือ และห้ามใช้
แทนชุด benchmark ภาพจริงใน [`evaluation/README.md`](../README.md) โดยเด็ดขาด**

- ภาพสังเคราะห์ render จากฟอนต์คอมพิวเตอร์ ไม่มี texture กระดาษจริง แสงจริง
  เงาจริง หรือความผิดเพี้ยนจากเลนส์กล้องจริง ต่อให้จำลอง augmentation
  สมจริงแค่ไหนก็ยังเป็นการประมาณเท่านั้น
- **CER จากชุดสังเคราะห์และ CER จากชุดภาพถ่ายจริงต้องไม่ถูกนำมารวมเป็นคะแนน
  เดียวกันเด็ดขาด** ต้องรายงานแยกกันเสมอ - `evaluate_ocr.py` ระบุประเภทชุด
  ข้อมูล (`synthetic` หรือ `real_camera`) ไว้ที่หัวรายงานเสมอ และจะปฏิเสธไม่
  ทำงานทันทีถ้า manifest มีทั้งแถว synthetic และแถวจริงปนกัน (ดูหัวข้อ
  "ป้องกันการรวมคะแนนผิดชุด" ด้านล่าง)
- **ห้ามใช้ชุดสังเคราะห์นี้ fine-tune โมเดล OCR ใด ๆ** เครื่องมือชุดนี้ไม่ได้
  ออกแบบมาเพื่อสร้างข้อมูลฝึกโมเดล
- **ชุดภาพถ่ายจริงใน `evaluation/images/` ยังคงจำเป็นเสมอ** และต้องไม่ถูกใช้
  ปนกับข้อมูลสังเคราะห์ทั้งตอนฝึกและตอนทดสอบ (ดูหัวข้อ leakage ด้านล่าง)
- ประโยชน์ที่แท้จริงของชุดสังเคราะห์คือ: ทดสอบว่า pipeline preprocessing/
  evaluation ทำงานถูกต้องหรือไม่ (regression test แบบ deterministic),
  เปรียบเทียบพฤติกรรมคร่าว ๆ ระหว่างโหมด preprocessing ก่อนไปทดสอบกับภาพจริง,
  และสร้างเคสทดสอบสำหรับสภาพแสง/มุมที่หาภาพจริงมาครอบคลุมได้ยาก

## 1. รูปแบบไฟล์ corpus

Corpus คือ CSV ของข้อความต้นทางที่รู้ ground truth แน่นอน (ดูตัวอย่างใน
`corpus.example.csv`) มี 4 คอลัมน์:

| คอลัมน์         | ความหมาย                                                     |
|-----------------|------------------------------------------------------------------|
| `text_id`       | รหัสไม่ซ้ำของข้อความแต่ละรายการ (ใช้เป็นฐานของ group_id)         |
| `ground_truth`  | ข้อความที่ต้องการให้ render (จะถูกทำ Unicode NFC normalization) |
| `language`      | `th`, `en`, หรือ `mixed` ใช้จัดกลุ่มผลลัพธ์เท่านั้น               |
| `notes`         | หมายเหตุอิสระ ไม่ถูกใช้ในการคำนวณ                                 |

`corpus.example.csv` ที่ track ไว้ใน Git มีแถวตัวอย่างที่ระบุชัดเจนว่า **"ตัวอย่าง
เท่านั้น"** ในคอลัมน์ notes - ใช้เพื่อสาธิตรูปแบบไฟล์และครอบคลุมกรณีสำคัญ (ไทย
ล้วน, อังกฤษล้วน, ไทยปนอังกฤษ, ตัวเลข, เครื่องหมายวรรคตอน, สระ/วรรณยุกต์ที่ยื่น
เหนือ/ใต้บรรทัด) **ไม่ใช่ผลการประเมินจริงและไม่ควรถูกอ้างว่าเป็นเช่นนั้น**

สร้าง corpus ของคุณเองเป็น `evaluation/synthetic/corpus.csv` (ถูกกันออกจาก Git
โดย `.gitignore` แล้ว) หากต้องการชุดข้อความที่ใหญ่ขึ้นหรือเฉพาะทางมากขึ้น

## 2. การเตรียมฟอนต์ (Fonts)

เครื่องมือนี้**ไม่ดาวน์โหลดหรือ bundle ฟอนต์ใด ๆ ให้** และ**ไม่ใช้ฟอนต์ของระบบ
ปฏิบัติการเป็นค่าเริ่มต้น** (ไม่มี hardcoded path ของ macOS หรือระบบใด ๆ) คุณ
ต้องระบุ `--font-dir` ชี้ไปยังโฟลเดอร์ที่มีไฟล์ `.ttf`/`.otf` ของคุณเองเสมอ
(ไม่รองรับ `.ttc`/`.dfont`)

**คำเตือนเรื่อง license**: คุณต้องตรวจสอบเองว่าฟอนต์ที่ใช้อนุญาตให้นำไป render
ภาพลักษณะนี้ได้ตามเงื่อนไข license ของฟอนต์นั้น เครื่องมือนี้ไม่ตรวจสอบ license
ให้ และไฟล์ฟอนต์จะไม่ถูก copy หรือ commit เข้าโปรเจกต์นี้ไม่ว่ากรณีใด (คุณเก็บ
ไฟล์ฟอนต์ไว้นอกโฟลเดอร์โปรเจกต์นี้ก็ได้)

**คำเตือนเรื่องความครอบคลุมตัวอักษรไทย (Thai glyph coverage)**: ฟอนต์บางตัว
(โดยเฉพาะฟอนต์ที่เน้นภาษาอังกฤษ) ไม่มีตัวอักษรไทยครบ หรือวาดสระ/วรรณยุกต์ผิด
ตำแหน่ง เครื่องมือนี้มีการตรวจสอบ coverage แบบ **heuristic** ก่อน render ทุก
ครั้ง (เทียบ bounding box ของตัวอักษรกับ .notdef glyph ของฟอนต์) และจะข้าม
(นับเป็น failure ใน run_metadata.json) หากพบตัวอักษรที่ดูเหมือนไม่มีในฟอนต์
**นี่ไม่ใช่การตรวจสอบ cmap แบบสมบูรณ์** (ต้องใช้ fontTools ซึ่งไม่ได้เป็น
dependency ของโปรเจกต์นี้) จึงอาจพลาดบางกรณี **แนะนำให้ตรวจสอบด้วยสายตาเองว่า
ภาพตัวอย่างที่ generate ออกมาแสดงสระ/วรรณยุกต์ไทยถูกต้อง** ก่อนใช้ผลจริง

## 3. รันการ generate

```bash
source .venv/bin/activate
python generate_synthetic_ocr.py \
    --corpus evaluation/synthetic/corpus.example.csv \
    --font-dir /path/to/approved-fonts \
    --output evaluation/generated \
    --run-name baseline-seed-42 \
    --variants-per-text 5 \
    --seed 42
```

**หมายเหตุ**: ตัวอย่าง path `/path/to/approved-fonts` ด้านบนเป็นเพียงตัวอย่าง
รูปแบบคำสั่งเท่านั้น **ไม่มีอยู่จริง** ต้องแทนที่ด้วยโฟลเดอร์ฟอนต์จริงของคุณ

ตัวเลือกอื่น ๆ ที่ปรับได้ (ดูค่าเริ่มต้นทั้งหมดด้วย `--help`):

```bash
# กำหนดขนาดฟอนต์, สี, ระยะขอบ เอง
python generate_synthetic_ocr.py --corpus ... --font-dir ... --output ... \
    --run-name custom --seed 7 \
    --font-sizes 24 32 40 --fg-color 10,10,10 --paper-color 250,248,240 \
    --margin-px 24 --line-spacing 1.4

# แบ่ง train/val/test โดยกันการรั่วไหลระหว่าง split (แบ่งตาม text_id เสมอ)
python generate_synthetic_ocr.py --corpus ... --font-dir ... --output ... \
    --run-name split-demo --seed 7 --variants-per-text 6 \
    --splits "train:0.7,val:0.15,test:0.15"

# บันทึกเป็น JPEG แทน PNG (แยกจาก variant "jpeg_compressed" ที่จำลอง artifact
# ที่ระดับพิกเซลอยู่แล้วไม่ว่าจะเลือกฟอร์แมตไฟล์ใด)
python generate_synthetic_ocr.py --corpus ... --font-dir ... --output ... \
    --run-name jpg-demo --seed 7 --image-format jpg --jpeg-quality 85
```

การรันซ้ำด้วย `--corpus`, `--font-dir`, และ `--seed` เดียวกัน **ให้ไฟล์ภาพและ
ค่าพารามิเตอร์ augmentation เหมือนเดิมทุกไบต์** ส่วน `--seed` ที่ต่างกันให้ผล
augmentation ที่ต่างกัน (แม้ corpus/font เดิม) เครื่องมือนี้จะ**ปฏิเสธเขียนทับ
run เดิมโดยไม่ตั้งใจ** - ถ้า `--run-name` ซ้ำกับ run ที่มีผลลัพธ์อยู่แล้ว ต้อง
ระบุ `--force` อย่างชัดเจน (และจะไม่ลบโฟลเดอร์เดิมไม่ว่ากรณีใด)

```
evaluation/

      manifest.csv          ใช้กับ evaluate_ocr.py ได้ทันที

                             จำนวนสำเร็จ/ล้มเหลว
```

## 5. คอลัมน์ใน manifest ที่ generate ได้

นอกจาก 4 คอลัมน์ที่ `evaluate_ocr.py` ต้องใช้ (`image_path`, `ground_truth`,
`language`, `notes`) manifest ที่ generate ได้มีคอลัมน์ metadata เพิ่มเติม:

| คอลัมน์                   | ความหมาย                                                      |
|----------------------------|--------------------------------------------------------------|
| `sample_id`                | รหัสเฉพาะของภาพนี้                                             |
| `source_text_id`           | `text_id` ต้นทางจาก corpus                                    |
| `group_id`                 | รหัสกลุ่ม - ภาพทุกใบจากข้อความต้นทางเดียวกันมี group_id เดียวกัน |
| `split`                    | `train`/`val`/`test` (ว่างเปล่าถ้าไม่ได้ระบุ `--splits`)         |
| `font`                     | ชื่อไฟล์ฟอนต์ที่ใช้ render ภาพนี้                                |
| `font_size`                | ขนาดฟอนต์ (px) ที่ใช้                                          |
| `seed`                     | seed หลักของการรัน run นี้                                     |
| `variant`                  | หมวดหมู่ augmentation (`clean`, `dark`, `rotated`, ฯลฯ)         |
| `augmentation_parameters`  | JSON ของค่าพารามิเตอร์ augmentation ที่สุ่มได้จริงสำหรับภาพนี้    |
| `synthetic`                | `true` เสมอสำหรับทุกแถวที่ generate ได้                         |

`ocr_evaluation.load_manifest` (ที่ `evaluate_ocr.py` ใช้) รองรับคอลัมน์เพิ่ม
เติมเหล่านี้แบบ backward-compatible - manifest ภาพจริงแบบเดิม (มีแค่ 4 คอลัมน์)
ยังคงใช้งานได้เหมือนเดิมทุกประการ

## 6. Augmentation ที่รองรับ

| หมวดหมู่ variant       | จำลองอะไร                                                         |
|--------------------------|--------------------------------------------------------------------|
| `clean`                   | ข้อความ render ปกติ ไม่มี augmentation (baseline)                    |
| `dark`                    | ภาพมืด (brightness ลด + gamma)                                     |
| `bright`                  | ภาพสว่าง/แสงจ้า (brightness เพิ่ม + gamma)                          |
| `low_contrast`            | contrast ต่ำ (ตัวอักษรกับพื้นหลังใกล้เคียงกัน)                        |
| `rotated`                 | ภาพเอียงเล็กน้อย (2-8 องศา)                                         |
| `perspective`             | มุมกล้องเอียง (perspective warp เล็กน้อย)                            |
| `zoomed_out`               | ถ่ายไกลเกินไป (ข้อความเล็กลง มีพื้นที่ว่างล้อมรอบมากขึ้น)              |
| `blurred`                 | เบลอ (Gaussian blur หรือ motion blur แบบสุ่มเลือก)                   |
| `noisy`                   | Sensor noise (Gaussian noise)                                      |
| `jpeg_compressed`         | JPEG compression artifact (คุณภาพต่ำ)                                |
| `combined_camera_like`    | ผสมหลายอย่างข้างต้นพร้อมกันแบบสุ่ม (3-5 อย่าง) ด้วยความรุนแรงลดลง เพื่อจำลองภาพถ่ายจริงที่มักมีหลายปัญหาผสมกันเบา ๆ |

นอกจากนี้ยังมี primitive เพิ่มเติมที่ใช้ประกอบกันได้ (โดยเฉพาะใน
`combined_camera_like`): grayscale conversion, แสงไม่สม่ำเสมอ/เงา gradient,
downscale แล้ว upscale กลับ, สีกระดาษแปรผันเล็กน้อย, และการเลื่อนภาพเล็กน้อย
แบบปลอดภัย (ไม่ดันข้อความหลุดขอบ)

**ช่วงค่าพารามิเตอร์ทั้งหมดตั้งใจไม่ให้รุนแรงสุดโต่งเสมอไป** (สุ่มในช่วงที่
สมเหตุสมผล ไม่ทำให้ภาพเสียหายจนอ่านไม่ออกทุกภาพ) ดูค่าคงที่และช่วงทั้งหมดที่
คอมเมนต์อธิบายไว้ใน `synthetic_dataset.py` (คลาส `AugmentConfig`)

ทุกภาพมีการเผื่อขอบ (padding) รอบข้อความก่อนทำ transform ทางเรขาคณิต (หมุน/
perspective/เลื่อน) และการหมุนใช้ `expand=True` เสมอ เพื่อไม่ให้ตัวอักษรไทย
ที่มีสระ/วรรณยุกต์ยื่นเหนือ-ใต้บรรทัดถูกตัดขอบ

## 7. Reproducibility (การทำซ้ำผลได้แน่นอน)

- `--seed` เดียวกัน + `--corpus`/`--font-dir` เดียวกัน + เวอร์ชัน dependency
  เดียวกัน (Pillow/numpy/opencv) → ได้ไฟล์ภาพและ `augmentation_parameters`
  เหมือนเดิมทุกไบต์เสมอ ไม่ว่าจะรันกี่ครั้งหรือลำดับการประมวลผลภายในเปลี่ยนไป
  อย่างไร (แต่ละภาพใช้ RNG ที่ seed แยกจาก seed หลัก + text_id + variant เอง)
- `--seed` ต่างกัน → ได้พารามิเตอร์ augmentation ต่างกัน (แต่ยังอยู่ในช่วงที่
  กำหนดไว้)
- `run_metadata.json` บันทึก seed, SHA-256 ของไฟล์ corpus, รายชื่อไฟล์ฟอนต์ที่
  ใช้จริง, และค่าคอนฟิกทั้งหมด เพื่อให้ตรวจสอบย้อนหลังได้ว่า run หนึ่ง ๆ ถูก
  สร้างจากอะไร

## 8. ป้องกันการรั่วไหลของข้อมูล (Leakage Prevention)

ภาพทุกใบที่มาจากข้อความต้นทาง (`text_id`) เดียวกัน (ไม่ว่าจะต่างฟอนต์/ขนาด/
variant ก็ตาม) จะมี **`group_id` เดียวกันเสมอ**

เมื่อระบุ `--splits` เครื่องมือจะ**แบ่งตาม `group_id` เท่านั้น ไม่เคยแบ่งตาม
ภาพแต่ละใบ** - ข้อความต้นทางหนึ่งรายการจะอยู่ใน split เดียวเท่านั้นเสมอ (ทุก
ฟอนต์/ทุก variant ของข้อความนั้นอยู่ split เดียวกันหมด) การกำหนด split เป็น
deterministic จาก seed และเครื่องมือจะ**ตรวจสอบและ raise error ทันทีถ้าพบว่า
`group_id` ใดถูกกระจายไปมากกว่าหนึ่ง split** ก่อนเขียนไฟล์ผลลัพธ์ (ดูฟังก์ชัน
`validate_no_leakage` ใน `synthetic_dataset.py`)

**ข้อควรระวังที่สำคัญกว่านั้น** (เครื่องมือนี้ตรวจสอบให้ไม่ได้โดยอัตโนมัติ
ต้องระวังเอง):

- **ห้ามใช้ชุดสังเคราะห์นี้เป็นทั้งข้อมูลฝึกและข้อมูลทดสอบพร้อมกัน** ต่อให้แบ่ง
  split ถูกต้องตาม group_id แล้วก็ตาม เพราะภาพสังเคราะห์ทั้งหมดมาจาก
  distribution เดียวกัน (ฟอนต์/การ render เดียวกัน) การฝึกและทดสอบด้วยข้อมูล
  สังเคราะห์อย่างเดียวจะประเมินความสามารถทั่วไปของโมเดลผิดพลาด
- **ชุดภาพถ่ายจริงใน `evaluation/images/` ต้องแยกจากชุดสังเคราะห์นี้เสมอ
  และห้ามนำไปใช้ fine-tune โมเดลเด็ดขาด** (ตามที่ระบุไว้ใน
  [`evaluation/README.md`](../README.md) อยู่แล้ว)
- **CER ของชุดสังเคราะห์และ CER ของชุดภาพจริงต้องไม่ถูกนำมารวมเป็นคะแนน
  เดียวกัน** ต้องดูแยกกันเสมอเมื่อประเมินคุณภาพระบบจริง

## 9. รันประเมินผลด้วย `evaluate_ocr.py`

Manifest ที่ generate ได้ใช้กับตัวประเมินเดิมได้ทันที:

```bash
python evaluate_ocr.py \
    --manifest evaluation/generated/baseline-seed-42/manifest.csv \
    --output evaluation/results/baseline-seed-42.csv
```

รายงานจะระบุที่หัวรายงานชัดเจนว่าเป็นชุดข้อมูล **synthetic** (ตรวจจากคอลัมน์
`synthetic` ใน manifest โดยอัตโนมัติ) พร้อมสรุปแยกตามภาษา, โหมด preprocessing,
และ **variant การ augmentation** เพิ่มเติมจากเดิม

**ห้ามส่ง manifest ที่มีทั้งแถวสังเคราะห์และแถวภาพจริงปนกันเข้า `evaluate_ocr.py`
ในการรันเดียว** - ถ้าตรวจพบทั้งสองแบบปนกันในไฟล์เดียว เครื่องมือจะหยุดทำงาน
ทันทีพร้อมข้อความอธิบาย แทนที่จะคำนวณ CER รวมที่ทำให้ตีความผิด ให้แยกรัน
`evaluate_ocr.py` สองครั้งสำหรับสองชุดข้อมูลแทน

## 10. การตีความ CER ของชุดสังเคราะห์

CER (Character Error Rate) ที่วัดได้จากชุดสังเคราะห์บอกได้แค่ว่า **pipeline
ทำงานถูกต้องหรือไม่ในเชิงกลไก** (เช่น preprocessing บาง mode ทำให้ CER แย่ลง
อย่างเห็นได้ชัดบนภาพ clean หรือไม่, EasyOCR อ่านตัวเลข/เครื่องหมายวรรคตอนได้
หรือไม่) **ไม่ใช่ตัวชี้วัดว่าระบบจะทำงานได้ดีแค่ไหนกับภาพถ่ายจริง** เพราะ
ภาพสังเคราะห์ไม่มีความหลากหลายของกล้อง แสงจริง พื้นผิว หรือมุมมองแบบภาพถ่าย
จริง **ห้ามนำ CER ของชุดสังเคราะห์ไปสรุปว่าโหมด preprocessing ใด "เหมาะกับ
production"** ต้องยืนยันด้วยชุดภาพถ่ายจริงเสมอ (ดู
[`evaluation/README.md`](../README.md))
